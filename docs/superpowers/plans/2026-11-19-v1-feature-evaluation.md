# MyCodexSetting 1.0 평가 계획 · Context Rot 완화 효과

**2026-11-19 · 파일럿 중단 · [실제 진행 기록](../validation/2026-11-19-context-rot-pilot.md)**

평가 질문은 하나다. **같은 과제의 문맥이 길고 혼잡해질 때, JIT 원본 탐색·세션 인계·문맥 압축은 각각 정확도 하락을 얼마나 줄이는가?** 여기서 Context Rot은 필요한 근거를 이용할 수 있는데도 문맥 부담이 커질수록 유효한 제약을 잊거나, 폐기된 결정을 따르거나, 검증 상태를 혼동해 실제 과제를 틀리는 현상으로 측정한다.

## 효과를 계산하는 방법

같은 과제 하나를 독립된 네 조건에서 실행한다. 짧은 조건과 긴 조건에 **같은 정답, 유효한 제약, 폐기된 지시, 최종 질문**을 둔다. 긴 조건에는 답을 바꾸지 않는 작업 이력·유사 문서·도구 출력이 더 들어간다. 기능 ON/OFF에는 같은 자료와 질의를 제공한다. 정확도는 아래 네 항목의 득점률이다.

| | 짧은 문맥 | 긴 문맥 | 문맥 부담에 따른 하락폭 |
|---|---:|---:|---:|
| 기능 OFF | A | B | A − B |
| 기능 ON | C | D | C − D |

**완화 효과(%p) = (A − B) − (C − D).** 양수면 기능을 켰을 때 문맥 부담으로 잃은 정확도가 더 적었다. 긴 조건에서 사용자가 실제로 얻는 차이 **D − B**도 함께 보고한다. 예를 들어 OFF가 90%→65%, ON이 90%→82%라면 하락폭은 25%p와 8%p이고 완화 효과는 **17%p**다. 이 숫자는 계산 예시다.

## 세 기능의 실험

| 기능 | OFF / ON | 어떤 실패를 어떻게 확인하는가 |
|---|---|---|
| **JIT 원본 탐색** | 양쪽 모두 같은 파일·검색 도구에 접근한다. OFF는 일반 파일 탐색, ON은 프로젝트의 `.context/index.md`와 요청별 원본 선택 지침을 사용한다. 인계와 추가 압축은 양쪽에서 끈다. | 최신 승인값, 폐기된 값, 이름이 유사한 타 작업 문서를 함께 둔다. 최종 산출물이 **현재 값과 여전히 유효한 예외를 모두 적용했는지** 독립 검사한다. 실제로 열어 본 원본·구버전·무관 파일과 입력 토큰을 기록한다. [원본 탐색 정책](../../../kit/context-policy.md) |
| **세션 인계** | 네 조건 모두 첫 세션을 닫고 이전 대화가 없는 새 세션에서 재개한다. OFF도 같은 시간·권한으로 자유 형식 메모를 남기고 찾을 수 있다. ON은 `session-handoff`와 최신 인계 포인터를 사용한다. 공통 원본 인덱스와 검색 권한은 동일하다. | 첫 세션에 **아직 유효한 결정, 완료된 검증, 미실행 검증**을 둔다. 인계를 쓴 뒤 재개 전에 요구사항 하나를 양쪽에서 같은 방식으로 변경한다. 새 세션이 유효한 결정은 이어가고 오래된 값은 고쳐 **올바른 다음 행동**을 수행하는지 본다. 인계 작성 비용도 합산한다. [인계 절차](../../../kit/skills/session-handoff/SKILL.md) |
| **문맥 압축** | Windows CLI에서는 native와 `compression codex`, Paseo에서는 직접 제공자와 관리 bridge를 각각 비교한다. Codex 자체 자동 압축, 원본 접근권, 도구 출력 순서, 질문은 양쪽이 같다. | 초반·중간·후반에 배치한 근거에서 **남겨야 할 예외와 폐기해야 할 값**을 구별해 실제 변경에 적용하는지 채점한다. proxy 경유, 기본 자동 압축, 추가 압축·검색·복원을 구분해 기록한다. 블록이 만들어져도 실제 답이 틀리면 오답이다. CLI·Paseo 효과는 따로 산출한다. [CLI 검증 기록](../validation/2026-11-12-billion-context-cli.md) · [Paseo 검증 기록](../validation/2026-11-12-billion-context-paseo.md) |

기존 합성 시험에는 CLI에서 원문 표식을 복원하고 변경된 PRD를 구현한 사례가 있다. CLI 집계 `tokensSaved`는 0이었고, Paseo에서는 특정 합성 블록에서 2,820이 기록됐다. 어느 기록에도 위 네 조건의 정확도는 없다. 새 평가의 비교 기준선은 같은 버전에서 새로 실행한다.

## 과제와 채점

한 과제에는 다음 네 가지를 모두 넣는다. 각 항목은 숨겨 둔 정답표에 따라 0점 또는 1점이다. **주 지표**는 네 항목의 평균 정확도, **작업 성공률**은 네 항목을 모두 맞힌 과제의 비율이다. 오류 종류별 분모와 발생 건수도 공개한다.

| 채점 항목 | 정답을 판별하는 근거 |
|---|---|
| 최신 결정 채택 | 예전 값과 새 승인값 중 최종 결과가 새 값을 사용하는지 확인한다. |
| 유효한 예외 보존 | 새 결정에도 유지되는 오래된 예외를 실제 산출물의 경계값 테스트로 검사한다. |
| 검증 상태 구분 | 성공·실패·미실행 상태를 독립 실행 기록과 대조한다. 하지 않은 검사를 통과로 보고하면 0점이다. |
| 다음 행동 수행 | 남은 과제를 맞게 선택해 실행하고 기대 산출물을 만드는지 확인한다. 인계 양식이나 표식 복사만으로 점수를 주지 않는다. |

예시 과제는 “재시도 기본값을 3→7로 변경하되 결제 요청은 1회로 유지하며, 재개 시 아직 실행하지 않은 경계값 검사를 수행”하는 것이다. 실제 과제는 새 값·파일명·근거 위치를 바꿔 만든다. 양쪽에 같은 모순 자료를 주고, 정보 위치는 과제들 사이에서 초반·중간·후반에 균형 배치한다. 별도 진단으로 길이가 비슷한 자료에서 구버전 방해 문서 유무를 바꿔 보면, 단순 길이와 상충하는 정보의 영향을 구별할 수 있다. 이 진단값은 주 효과와 분리한다.

## 실행 설계와 합격 기준 제안

1. **모델별로 비교 조건을 동결한다.** 0.5.1 스냅샷(SHA-256 `e264485389e761abea00cc005b15b2f7b2f54351fc04859d68b69883b5cb7ea3`인 ZIP)에서 `gpt-6.2-sol`, `gpt-6.1-terra`, `gpt-6-luna`가 각자 같은 과제와 네 조건을 모두 수행한다. 세 모델 모두 추론 강도는 `xhigh`다. 평가 실행에 한해 공통 컨텍스트 창 272,000과 기본 자동 압축 기준 231,200(85%)을 제안한다. 이 PC의 Codex 모델 캐시에 표시된 기본 창은 Sol·Terra 500,000, Luna 272,000이며 세 모델의 최대 창 표시는 872,000이다. 실행 때 각 호스트의 모델 ID와 유효 설정을 확인하고, 설정을 맞출 수 없는 조합은 미검증으로 기록한다. 합성 자료·정답표·도구·권한·턴 한도를 고정하고 새 세션마다 독립 복제본을 사용한다. 모델 순서와 모델 안의 네 조건 실행 순서를 균형 배정한다. [공식 모델 목록](https://developers.openai.com/api/docs/models)
2. **자료량과 실제 노출량을 나눠 기록한다.** 파일럿 시작 후보는 관련 근거가 같은 약 8천·6만4천 토큰의 합성 자료다. JIT는 탐색 가능한 문서, 인계는 첫 세션의 이력, 압축은 시간순 도구 출력을 늘린다. 입력 자료의 크기·턴 수와 모델이 실제 받은 입력 토큰을 각각 기록한다. JIT가 덜 읽거나 압축으로 입력이 짧아지는 변화가 바로 측정할 작동 경로다. 서로 다른 기능 간 순위는 같은 부담을 재현한 경우에만 해석한다.
3. **승인 후 파일럿을 실행한다.** CLI에서 3개 모델 × 3개 기능 × 1과제 × 짧음/김 × OFF/ON = **최대 36개 워크플로**다. 인계 워크플로는 각각 두 세션이다. 파일럿은 채점·격리·열화 재현·압축 관측과 비용을 확인하는 용도다. 기존 제안 상한 **세 모델 합계 30분·요금표 환산 US$15** 내에서 모델·기능별 네 조건을 한 묶음으로 실행한다. 미완료 묶음은 명시하며 파일럿 결과를 본 실험의 분모에 포함하지 않는다.
4. **본 실험은 별도 승인한다.** 파일럿 후 새 과제와 동일한 채점 규칙을 동결한다. 기능·호스트별 독립 과제 12개, 과제당 2회 반복을 출발점으로 세 모델에 동일 과제를 배정하고, 분산·검출하려는 차이·예산으로 최종 표본 수를 정한다. 각 모델 안에서 같은 과제의 네 조건을 한 묶음으로 유지하고 반복은 먼저 평균한다. 모델·기능·호스트별로 과제를 재표집해 완화 효과와 95% 구간을 산출한다. Trace에는 실제 모델 ID·추론 강도를, 비용에는 해당 모델 요율을 기록한다. 미발동·타임아웃도 배정 결과에 남기며 유효 묶음 수와 누락 사유를 공개한다.
5. **세 기능을 함께 쓰는 결과**는 본 실험에서 동일한 두 세션 과제로 세 기능 전부 OFF와 전부 ON을 짧음/김 각각 비교해 별도로 보고한다. 개별 효과를 더해 조합 효과로 추정하지 않는다.

**판정 기준은 실측 전 제안값이다.** OFF 하락폭의 95% 구간 하한이 0보다 커야 해당 과제가 Context Rot을 재현했다고 판정한다. 그 조건에서 다음 기준을 적용한다.

| 판정 | 기준 |
|---|---|
| **PASS** | 완화 효과 점추정치가 **10%p 이상**이고 95% 구간 하한이 0보다 높다. 긴 조건의 ON 정확도도 OFF보다 높고, 짧은 조건의 ON−OFF 정확도 하한(95%)은 −5%p 이상이어야 한다. 짧은 조건에서 ON만 성능이 떨어져 차이가 커지는 경우를 걸러낸다. |
| **FAIL** | 열화가 재현되고 유효 표본을 확보했는데도 완화 효과 95% 구간 상한이 10%p 미만이거나, 긴 조건의 ON 정확도가 OFF보다 낮다는 결과가 95% 구간에서 확인된다. 보호 자료 훼손은 효과 크기와 별도로 승격을 중단할 사유다. |
| **미검증** | OFF에서도 뚜렷한 하락이 없거나, 구간이 판정 경계를 걸치거나, 호스트·표본·관측 근거가 부족하다. 압축이 일부 시도에서 발동하지 않으면 그 시도도 포함하되, 해당 호스트에서 실제 압축을 한 번도 관측하지 못하면 압축 메커니즘의 효과는 미검증이다. |

**보조 지표**로 과제 전체의 입력·캐시 입력·출력 토큰, 성공 1건당 비용, 경과시간, 재시도, 불필요한 읽기와 근거 없는 완료 주장을 기록한다. 요청 ID로 usage를 중복 제거하고 인계 작성·재개와 복원 호출을 포함한다. 실청구와 요금표 환산 비용을 구분하고 관측되지 않은 수치는 미상으로 둔다. 토큰이 줄어도 정확도 하락이 그대로면 Context Rot 완화 점수를 주지 않는다.

## 증거 기록과 1.0 판단

기존 도구의 턴 usage 수집·증거 해시 대조와 실제 산출물의 요구값 검사를 재사용한다. 실행 전에 기존 runner의 고정 모델명과 변형별 프롬프트 치환을 분리한다. 공개 예시의 정답은 본 평가에 재사용하지 않는다. 실행 원장은 새 경로에 두고 기존 결과와 사용자 데이터를 보존한다. [턴 수집 도구](../../../tools/evaluations/hallmark/run.py) · [증거 대조](../../../tools/evaluations/hallmark/collect.py) · [기존 워크플로 검사](../../../tests/integration/test_compression_workflow.py)

Langfuse 주소·키는 현재 프로세스에 설정되어 있지 않다. 연결 준비 시 평가 전용 프로젝트의 `LANGFUSE_BASE_URL`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`를 전송 프로세스에만 주입한다. 목적지와 필드가 승인되면 실행별 Trace에 익명 과제 ID, 기능·호스트·부담·ON/OFF, 네 항목 점수, usage·시간·비용·증거 해시를 연결하고 조회로 확인한다. 그전에는 로컬 원장만 사용한다. 원문·키·사용자 경로는 전송 대상에서 제외한다. [Langfuse 연결 안내](https://langfuse.com/docs/observability/get-started)

**로컬 관측 환경 준비 기록 (2026-11-19).** 평가 전용 `.venv-eval`에 Python 3.13.2와 `langfuse==5.2.0`을 구성했고 `pip check`를 통과했다. SDK의 메모리 span exporter와 모의 HTTP 전송으로 합성 span 1건·점수 1건의 Trace ID 일치를 확인했다. 이 점검의 소켓 연결은 0건이다.

**Cloud 준비 상태.** 사용자가 Langfuse Cloud의 `MyCodexSetting-Eval`을 생성하고 로컬 터미널에서 프로젝트 조회 성공을 확인했다. 저장소 루트에서 `.\.venv-eval\Scripts\python.exe -X utf8 -B .\tools\evaluations\langfuse_check.py`는 읽기 전용 조회를 수행한다. `--smoke`로 실행하면 리전·키를 입력하고 대상 프로젝트를 확인한 뒤 합성 Trace 1건과 점수 1건의 전송을 선택할 수 있다. 같은 ID로 서버 조회까지 성공해야 `.venv-eval/cloud-smoke-verified.json`에 결과를 남긴다. [연결 확인 도구](../../../tools/evaluations/langfuse_check.py) · [공식 API 안내](https://langfuse.com/docs/api-and-data-platform/features/public-api)
