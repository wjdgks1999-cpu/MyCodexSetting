# Hallmark 기본 웹디자인 기능 호환성 Test Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to execute this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 실제 호스트의 새 세션을 시험하며, 검토용 하위 에이전트의 역할극을 호스트 호환성 증거로 대체하지 않는다.

**Goal:** Hallmark를 MyCodexSetting의 기본 웹디자인 기능으로 포함할 수 있는지, Superpowers 및 기존 기능과 함께 실행한 증거로 판정한다.

**Architecture:** 동일한 시험 프로젝트·요청·모델로 네 가지 스킬 구성을 비교한다. 설치 검사, 실제 다중 턴 실행, 브라우저 검증, 배포 후 재설치 검사를 나누고 원본 Hallmark와 수정 후보의 결과를 별도로 보존한다.

**Tech Stack:** 기존 Python 표준 라이브러리 설치·검증 도구, Codex CLI, Node.js, HTML/CSS/JavaScript 시험 페이지, 실행 시 확인한 브라우저 자동화 도구.

**Spec:** 아래 「요구사항과 판정 범위」의 사용자 요청. 제품 통합 설계의 승인을 의미하지 않는 테스트 계획이다.

**Status:** 사용자 결정으로 Hallmark 도입 보류. 1차 실제 평가 마감 상태이며, 전체 반복·확장 호스트 검증은 미실행이다. 재개 요청에 대비해 아래 체크리스트와 증거를 보존한다.

## 요구사항과 판정 범위

- 사용자는 MyCodexSetting에서 기본 제공할 웹디자인 스킬을 찾고 있다. 선택 설치를 전제로 결론 내리지 않는다.
- **기본 포함**은 새 프로젝트 설치 시 함께 제공하는 것, **자동 호출**은 이름을 말하지 않은 웹디자인 요청에도 선택되는 것이다. 둘을 별도 판정한다. 기존 네 관리 스킬은 기본 제공되며 명시 호출 정책을 쓴다.
- 코드·문서에서 충돌 가능성을 찾는 것은 가설 수립이다. 실제 호출·작업 순서·파일 변경·산출물·다음 세션의 행동을 시험해야 호환성 판정 근거가 된다.
- 충돌 없이 동작해도 웹디자인 기능의 품질이나 필수 의존성 때문에 기본 제공에 부적합할 수 있다. 기능 실패, 스킬 간 충돌, 환경 미준비를 구분한다.
- 이번 요청의 산출물은 계획이다. 아래 실행 체크리스트는 미실행으로 남기며 설치·제품 통합·배포를 진행하지 않는다.

2026-11-16 후속 승인: 사용자가 “좋습니다. 진행하세요.”로 이 계획의 테스트 실행을 승인했다. 위 문장은 계획 작성 당시 범위이며, 아래 격리 시험·시험 도구·결과 문서 작성은 현재 승인 범위다. 제품 기본 기능으로 통합하거나 게시하는 것은 별도다.

## Global Constraints

- Hallmark 2.0.0, commit `04977e15f3dfd6ee4b74c887dac3eb52665d6c92`를 고정한다. Superpowers는 현재 설치본의 파일별 해시를 실행 전에 고정한다.
- MyCodexSetting의 Git HEAD뿐 아니라 미커밋 변경과 `kit/` 해시도 기록한다. 개발용 루트 AGENTS 대신 **배포용** `kit/templates/AGENTS.md`로 새 소비자 프로젝트를 시험한다.
- 테스트는 독립 임시 Git 저장소에서 수행한다. 현재 프로젝트의 `.agents/`, `.mycodex/`, `.codex/`, 기존 `dist/`, 전역 스킬·설정·hooks는 변경하지 않는다.
- Hallmark의 전역 설치 스크립트를 실제 사용자 홈에 실행하지 않는다. 시험 저장소에 고정된 스킬 자산을 준비하고 발견 여부를 확인한다.
- 실제 인증을 복사하거나 출력하지 않는다. 연결 상태만 확인하고 로그에는 허용한 설정 항목·합성 입력·도구 결과만 남긴다. 외부 공개·Production 배포·유료 이미지 생성은 시험하지 않는다.
- `.human-docs/` 접근 시험은 새 fixture에만 적용한다. 현재 프로젝트의 기존 산출물은 읽거나 검색하지 않는다.
- 명령·검증 미실행, 도구 부재, 정책 차단은 `BLOCKED` 또는 `NOT_RUN`으로 남긴다. 테스트 대상이 능력을 사용할 수 없었다면 “충돌 없음”으로 처리하지 않는다.

## 비교 구성과 실행 조건

모든 구성에는 MyCodexSetting의 기존 네 관리 스킬과 동일한 호스트 기본 기능이 있다. S는 현재 Superpowers 설치본, H는 원본 Hallmark다.

| 구성 | 추가 스킬 | 목적 |
|---|---|---|
| B | 없음 | 기존 기능의 기준 동작 |
| S | Superpowers | 현재 개발 절차의 기준 동작 |
| H | Hallmark | Hallmark 단독의 기능·실패 확인 |
| SH | Superpowers + Hallmark | 동시 사용으로 발생하는 변화 확인 |

- 처음에는 원본을 그대로 시험한다. metadata 거부로 로딩이 실패하면 그것도 원본의 실패다. 수정 후 같은 원본 결과로 기록하지 않는다.
- 필요할 때만 후보 `SH-A`(호환 수정 + 자동 호출), `SH-E`(호환 수정 + 명시 호출)를 별도 만든다. 변경 diff와 해시를 고정하고 동일 사례를 재시험한다. 명시 호출 정책만 바꾼 후보라면 그 사실도 구분한다.
- 후보의 기본 포함 가능성을 검증하려면 “폴더 복사 성공”을 넘어 실제 kit 자산 목록·manifest·검증 정책·임시 ZIP을 거쳐 설치해야 한다.
- 자동 호출 후보는 S01·S02에서 이름을 지정하지 않아도 실제 Hallmark 로드·적용 증거가 있어야 한다. 끝내 호출되지 않으면 자동 호출 기능은 통과하지 못한다. SH-E는 이 두 사례의 자동 호출 부재를 확인한 뒤, 별도의 `$hallmark` 명시 입력으로 같은 작업을 완료해야 한다.
- 스킬 목록, 사용자/프로젝트 지침, 모델·추론 설정, 도구·권한, 작업 디렉터리, 네트워크, 입력 파일은 비교쌍에서 같게 한다. 차이는 시험할 스킬과 명시된 변수뿐이다.
- 숨은 전역 스킬은 세션 범위 설정으로 제외하고 실제 목록에서 확인한다. 전역 파일을 수정하거나 삭제하지 않는다. `CODEX_HOME`만 바꾸면 사용자 홈 스킬까지 격리된다고 가정하지 않는다.
- 모델은 배포 설정과 호스트에서 실제 사용할 수 있는 동일 모델로 고정한다. 자동 fallback이 발생하면 그 실행을 별도 분류한다. 매번 새 세션과 새 fixture를 쓰며 기억 읽기·쓰기는 비교 실험에서 제외하고 실제 기본 설정의 확인 실행을 별도로 한다.
- CLI 반복 시험과 사용자가 쓰는 앱/호스트 시험은 별도 결과다. 현재 대화의 스킬 목록에 추가된 것으로 가정하지 않고 새 세션의 발견·호출을 확인한다. CLI만 통과하면 앱 호환은 미검증으로 남긴다.

## 실제 세션의 입력·관측 방법

1. 한국어 PRD를 가진 두 fixture를 준비한다. 하나는 새 소개 페이지, 다른 하나는 기존 검색·필터·목록·문의 폼이 있는 데이터 서비스다. 문구, 식별자, 기본 색상, DOM 기능 검사, 변경 허용 경로를 고정한다.
2. 최초 요청은 아래 사례의 문장을 사용한다. 자동 호출 시험에는 Hallmark 이름이나 “두 스킬을 조율하라”는 힌트를 넣지 않는다. 명시 호출 시험에는 `$hallmark`를 사용한다.
3. 질문에는 고정된 사실표에서 답한다. 청중=한국어 공공데이터 이용자, 목적=자료 검색, 톤=차분하고 명료함, 자료=fixture 안의 문구와 로컬 SVG, 외부 이미지/API=사용하지 않음. 없는 답은 임의 생성하지 않고 기록한다.
4. 설계 제시 전에는 설계 승인·구현 허가를 주지 않는다. 요구사항이 충족된 설계를 실제로 받은 뒤 별도 사용자 턴으로 “제시한 설계대로 진행하세요”를 전달한다. 이미 승인된 사례는 승인 문서와 허용 범위를 처음부터 제공한다.
5. 실행기의 후속 턴은 시험용 사용자 응답임을 로그에 구분한다. 서로 다른 역할을 한 프롬프트에 합쳐 가상 대화를 만들지 않는다. 동일 세션을 ID로 재개하며 질문·승인·구현 순서를 보존한다.
6. JSONL 실행 이벤트, 스킬 로드 근거, 도구 호출, 턴별 파일 diff, stdout/exit code, 브라우저 결과를 수집한다. 에이전트의 “스킬 사용/검증 완료” 문장만으로 판정하지 않는다. 접근 관측이 불완전하면 그 검사는 미확인이다.
7. 정상 승인 대기는 실패가 아니다. 이미 답한 같은 질문을 새로운 사유 없이 두 번 더 묻거나, 같은 파일을 두 규칙에 맞춰 되돌리는 순환이 두 번 발생하면 절차 충돌로 기록한다. 사례당 20 사용자 응답 턴 또는 30분 초과는 `INCONCLUSIVE`로 중단하고 원인을 조사한다.
