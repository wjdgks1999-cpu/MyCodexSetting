# Codex CLI에서 세 가지 문맥 관리 기능의 효과를 평가하는 설계안

2026-11-20 · 다른 컴퓨터에서 수행할 실험 · 본시험 결과 없음

## 평가 질문과 범위

**일반 Codex CLI에서 실제로 실패한 과제·상황만 기능 효과 검증 대상으로 채택한다.** 먼저 세 기능을 모두 끄고 실패를 확인한다. 그 뒤 같은 시작 상태에서 해당 기능을 켰을 때 실패가 성공으로 바뀌는지, 그 과정에 시간과 토큰이 얼마나 드는지 측정한다. 평가 단위는 사용자 요청부터 결과 검증까지의 **과제 한 건**이다. [기능별로 해결하려는 문제](../../../PURPOSE.md)

| 확정한 선택 | 적용 범위 |
|---|---|
| 터미널 Codex CLI, `gpt-6-luna`, 사고 수준 `low` | 양쪽 모두 일반·계획 모드 `low`. 첫 단계는 합성 프로젝트만 사용한다. |
| 과제 채택 필수 조건 | 해당 기능이 해결하려는 문제와 연결된 정답·무도움 재개·완주 실패를 일반 Codex에서 재현해야 한다. 실패 재현 기준을 충족하지 못하거나 시간·토큰 초과만 있는 후보는 선별 기록에만 남긴다. |
| 새 세션으로 인계 | 새 CLI 대화에서 시작할 작업과 순서를 알려 준다. 인덱스가 있는 인계 비교에서만 위치를 안내한다. |
| Langfuse Cloud | 합성 과제 실행과 채점 결과를 수집한다. 현재 문서와 인계 작성은 평가 데이터에 포함하지 않는다. |
| 모델 확장 | Luna/low에서 효과를 확인한 기능만 다음 후보(`gpt-6-luna / medium`, `gpt-6.1-sol / low`)에서 하나씩 재검증한다. |

**실패를 먼저 재현하는 순서와 채택 조건은 필수다.** 반복 횟수·수치 합격선·표본 규모는 제안값이다. 파일럿에서 변동을 확인하고 본시험 후보를 열기 전에 확정한다.

## 일반 Codex에서 실패하는 과제 선정

1. **후보를 만든다.** 예컨대 “구버전 값을 구현한다”, “새 세션이 이미 확정된 제약을 재질문한다”, “장문 작업 후 초반 예외를 빠뜨린다”처럼 기능별로 관찰하려는 실패를 먼저 정의한다. 시작 스냅샷, 프롬프트, 기능에 보일 원본, 정답·필수 검증, 한도와 실패 판정식을 고정한다. 정답을 직접 준 쉬운 문항으로 기본 수행 능력과 도구 경로도 확인한다.
2. **일반 Codex만 먼저 실행한다.** JIT 인덱스·탐색 지침, 인계 파일·포인터, billion-context 경유를 모두 제외한다. 같은 파일을 검색할 수 있는 기본 CLI 도구와 Codex 내장 압축은 그대로 둔다. 기능을 켠 결과를 보기 전에 독립된 새 실행에서 동일 실패의 재현 횟수를 확인한다. 예시 규칙은 **미리 정한 3회 중 2회 이상**이다. 첫 실패가 나올 때까지 임의로 반복하지 않는다.
3. **증거로 채택한다.** 후보·버전별로 전체 시도 수, 성공·실패·보류, 실패한 테스트나 산출물, CLI trace ID를 남긴다. 정상 환경에서 사전 정의한 실패가 재현된 후보만 다음 단계로 보낸다. 단순 지연·토큰 사용 증가, 실험자 예산 초과, 인증·권한·런타임·계측 장애는 채택 근거에서 제외한다. 기준을 충족하는 후보가 0개면 해당 기능의 효과는 평가 보류다.
4. **채택한 과제에서 새로 비교한다.** 선별 실행은 본시험 대조군으로 재사용하지 않는다. 동일 스냅샷·채점표의 새 사본에서 기능 OFF와 ON을 독립 실행하고 같은 과제·반복 번호로 짝짓는다. 인계는 아래 표처럼 양쪽에 JIT를 동일하게 둬 인계의 추가 효과를 구분한다. OFF가 재실행에서 성공해도 쌍을 버리지 않는다. 후보를 수정하면 새 버전을 부여해 처음부터 선별한다.

## 비교 조건

각 쌍은 같은 업무·순서, 시작 데이터, CLI 실행 파일, 모델, 추론 수준, 도구 권한, 시간·턴 한도를 사용한다. 제품 저장소 밖에 조건별 작업 사본을 만든다. 초기화 전에 공통 실험 설정을 준비해 양쪽의 `.codex/config.toml`에 같은 내용으로 둔다. 기존 설정을 보존하는 설치 계약을 사용한다. Luna의 모델 기본값 또는 새 PC에서 확인한 동일한 문맥 창·내장 자동 압축 기준을 사용한다. Astra 배포 기본값인 100만/85만 토큰이 한쪽에 유입되면 바로잡고 다시 점검한다. [설치 동작](../../../kit/mycodex_lib/install.py) · [배포 설정](../../../kit/templates/config.toml)

각 사본의 시작 파일 목록·해시 및 **실제로 적용된 설정**을 로컬에 대조표로 남긴다. 실제 Codex 바이너리 경로·버전·해시, 모델·일반/계획 사고 수준, 문맥 창·자동 압축 기준, 신뢰·샌드박스·승인, hooks·MCP·스킬 목록을 비교한다. 서브 에이전트와 세션 간 메모리는 양쪽 모두 끈다. 조건표에서 허용한 차이 외의 관련 설정이 다르거나 그 동등성을 확인하지 못하면 해당 비교를 보류한다. 채점표·반대 조건·이전 로그는 평가 에이전트가 읽을 수 없는 위치에 두고, 같은 권한에서 무해한 표식 파일의 접근 차단도 점검한다.

| 기능 | 대조군 | 실험군 |
|---|---|---|
| JIT Retrieval | 같은 현행·구버전 문서와 코드를 제공한다. 일반 Codex가 파일을 자유롭게 검색하고 읽는다. 승인·시행·폐기 근거를 이 원본만으로 판별할 수 있어야 한다. | 같은 원본에 인덱스와 JIT 탐색 지침만 추가한다. 인덱스에는 원본의 위치·용도만 쓰고, ON에서만 알 수 있는 정답값이나 승인 사실을 넣지 않는다. [인덱스 작성 규칙](../../../kit/skills/project-init/SKILL.md) |
| 세션 인계 | JIT가 있는 공통 실험 사본에서 초기 조사와 엄격한 구조 검증을 마쳐 인덱스 상태가 `ready`인지 확인한 뒤 분기한다. 새 스레드에는 인덱스에서 관련 원본을 확인하라고 한다. | 같은 분기점에서 실제 `$session-handoff`를 실행한다. 새 스레드에는 최신 인계를 읽으라는 안내만 추가한다. 양쪽 모두 같은 업무와 순서를 준다. |
| billion-context | 같은 설치 사본·JIT/인계 상태에서 일반 CLI를 절대 경로와 `--no-daemon`으로 실행한다. | 동일한 CLI를 런타임에 고정하고 `compression codex`로 경유한다. 경유기가 추가하는 도구·압축·복원 외의 작업 조건을 맞춘다. |

인계의 **실패 선별**에서는 인덱스가 없으므로 “개편안부터 시작해 주세요”처럼 업무와 순서만 준다. 채택 후 본시험에서는 **인계 워크플로 전체**를 평가한다. 양쪽에 같은 첫 세션 중단 상태를 마련하고, ON의 인계 작성에만 그 대화 이력을 사용한다. 재개하는 두 스레드에는 이전 대화를 직접 주지 않는다. 인계 작성 전후의 파일 차이에서 스냅샷·최신 포인터와 스킬이 실제 갱신한 `AGENTS.md`·결정 문서 등을 기록한다. 최신 인계 파일만의 효과로 해석하려면 이 부수 변경까지 맞춘 별도 비교가 필요하다. 이후 세 기능을 모두 켠 종단 효과도 독립 과제로 측정할 수 있다. [세션 인계 동작](../../../kit/skills/session-handoff/SKILL.md)

## 합성 과제와 정답표

매 과제에 `case_id`, 시작 파일 해시, 양쪽의 사용자 프롬프트, 허용되는 다른 정답과 근거, 금지된 완료 주장, 채점 명령, 한도를 미리 기록한다. 파일 이름이나 정답값을 바꾼 쌍둥이 사례가 파일럿과 본시험에 걸치지 않도록 과제 유형 단위로 분리한다.

| 예시 | 준비와 요청 | 관찰할 결과 |
|---|---|---|
| JIT · 요구사항 충돌 | 과거 계획은 재시도 3회, 현행 PRD는 7회로 두고 관련 없는 문서를 섞는다. “현재 요구사항대로 재시도 횟수를 수정하고 검사해 주세요.”라고 요청한다. 다른 사례에는 누락된 인덱스 참조를 둔다. | 숨은 테스트에서 현행 값이 적용됐는지, 폐기된 값을 채택했는지, 어떤 문서 구간이 모델에 얼마나 전달됐는지 확인한다. 과거 문서를 대조한 뒤 올바르게 폐기하는 것은 오답이 아니다. |
| 인계 · 챗봇 개편 | 첫 세션에서 기존 API 형식 유지에 합의하고 질문 유형 하나는 미결정으로 남긴다. 양쪽 새 세션에 “개편안 → 질문 테스트 데이터 → 구현” 순서를 준다. 요구사항 변경 사례는 분기 후 재개 전에 양쪽 원본에 같은 변경을 가한다. | 첫 개편안이 API 제약과 최신 원본을 지키는지 채점한다. 이미 확정한 내용의 재설명 요구는 실패이고, 아직 결정하지 않은 사항의 적절한 질문은 허용한다. 프롬프트에 준 순서를 반복하면 점수를 주지 않는다. |
| 압축 · 장문 중 예외 보존 | 초반에 예외 규칙을 주고 중간에 긴 합성 도구 출력과 작업을 끼운 뒤 예외를 사용하는 구현을 요청한다. 중간 출력만 줄인 짧은 버전은 부하 진단용으로 두고 장문 실패 해결률 분모에서 제외한다. | 숨은 테스트로 예외가 실제 적용됐는지 확인한다. 경유 ON 성공은 경유 조건의 결과다. 압축·복원이 해결에 기여한 사례로 표시하려면 해당 실행의 관련 블록·발동 시점과, 복원을 주장할 때에는 반환된 원문에서 그 예외를 회수한 근거까지 연결한다. 미발동 ON도 전체 비교에 남긴다. |

위 표는 후보 예시다. 각 예시의 실패 여부는 새 컴퓨터의 일반 Codex 실행에서 판정한다. **근거를 프롬프트에 직접 주는 문항**과 **근거가 단일 파일에만 있는 문항**은 환경 점검용으로 따로 둔다. 파일 접근과 도구 경로가 정상임을 확인한 뒤 모델이 읽기를 생략한 사례는 결과로 기록한다. 단순한 도구 미호출만으로 과제 실패를 판정하지 않는다.

## 지표 및 판정 제안

**첫 판정은 같은 과제에서 확인된 실패를 기능이 해결했는지다.** 본시험의 독립된 실행 쌍에서 OFF의 해당 실패와 ON의 과제 성공이 함께 관찰돼야 실패 해결 사례로 센다. 양쪽이 모두 실패하면 토큰·시간이 줄어도 실패 해결 건수는 0이다. 다음 수치는 실패 해결과 함께 살펴볼 기능별 목표다.

| 기능·문제 | 기능별 지표와 제안 합격선 | 품질 및 보조 지표 |
|---|---|---|
| JIT · 불필요한 문맥과 오래된 정보 | 과제당 **불필요한 열람 토큰 25% 이상 감소**. 모델에게 실제 반환된 문서·검색 결과에서 사전 채점표상 관련 구간 밖의 텍스트를 고정 토크나이저로 센다. 반복 열람도 누적한다. | 최종 성공률 하락 허용폭 5%p. 구버전이 있는 과제의 낡은 값 적용률과 현행 근거 확보율을 보고한다. 오래된 정보 문제가 개선됐다는 결론은 구버전 적용률 자체가 줄었을 때만 쓴다. |
| 인계 · 세션 간 맥락 단절 | **무도움 재개 성공률 15%p 이상 향상**. 새 세션이 한도 안에서 추가 설명 없이 채점표를 통과한 첫 산출물·행동을 내면 성공이다. | 중단 시점부터 첫 유효 산출물까지의 시간·입력 토큰에 인계 작성, 탐색, 재작업을 포함한다. 전체 완주율, 재설명 횟수, 중복 작업과 미실행 검사의 허위 완료 보고도 기록한다. |
| 압축 · 문맥 한도, 정보 열화, 토큰 부담 | 장문 과제당 **모든 모델 호출의 누적 실제 입력 토큰 15% 이상 감소**. 압축·검색·복원·재시도에 든 모델 호출도 포함한다. | 최종 성공률과 초반 예외의 정확한 적용률 각각 하락 허용폭 5%p. 짧음→긺에 따른 정확도 변화, 문맥 한도 중단률, 출력 토큰·지연·최대 입력량도 보고한다. 토큰 감소만으로 정보 열화 완화를 주장하지 않는다. |

- **JIT 탐색 비용.** 25% 기준의 분모·분자는 두 조건 모두 도구가 반환한 불필요 구간만 센다. 명시적으로 읽은 인덱스도 같은 규칙을 적용해 해당 과제와 무관한 행은 불필요 구간으로 센다. 자동 주입되는 지침은 이 열람 지표에서 제외하고, 별도로 지침·인덱스 전체 길이와 과제당 실제 총입력을 보고한다. 인덱스 길이 추정값을 이미 계측한 실제 입력에 더하지 않는다. 반환 구간을 관찰할 수 없으면 파일 크기로 대체하지 않고 JIT 주 지표를 보류한다.
- **성공·실패.** 성공은 지정한 산출물과 필수 검증을 모두 충족한 경우다. 정답 오류, 무도움 재개 실패, 산출물·필수 검증 누락은 근거와 함께 각각 표시한다. 여러 원인이 겹치면 태그는 모두 남기고 실패 과제는 한 번만 센다.
- **중단 원인.** 사전 점검을 통과한 환경에서 해당 기능 때문에 인계 작성·압축 경유·복원이 중단되어 과제를 끝내지 못하면 그 조건의 **완주 실패**로 센다. OFF 대상 실패 10건에 대응하는 ON이 1건 성공하고 경유기 오류로 9건 중단되면 해결률은 1/10이다. 실제 모델 문맥 한도로 중단돼도 완주 실패다. 실험자 예산 초과, 외부 인증·서비스 장애, 원인 미확정은 근거와 함께 별도 보류한다. 계측만 끊긴 경우 확인 가능한 산출물·테스트는 채점하고 관측이 빠진 지표만 결측 처리한다. 이미 확인한 실패는 남긴다.
- **집계.** 동일 과제 내 반복 평균을 구한 뒤 과제에 같은 가중치를 준다. 감소율은 `1 − 실험군 평균 / 대조군 평균`, 성공률 차이는 두 조건의 %p 차이다. 기준값이 0이면 절대 차이만 표시한다. 타임아웃과 실패까지 관측된 시간·토큰을 포함하고, 전체 실행 수·보류 수·성공 수를 함께 제시한다. 성공률은 전체 예정 실행 대비 확인된 성공을 하한, 보류가 모두 성공했을 때를 상한으로도 제시한다.
- **선별과 본시험의 분모.** 전체 후보 중 재현 기준을 충족한 수를 먼저 보고한다. 채택 집합에서 **실패 해결률 = OFF에서 대상 실패가 발생하고 ON에서 성공한 쌍 수 / OFF에서 대상 실패가 발생한 평가 가능 쌍 수**다. 분모가 0이면 판정 보류다. 별도로 채택 과제의 전체 실행 쌍에서 양쪽 성공·양쪽 실패·실패→성공·성공→실패·보류 수와 전체 성공률 차이를 보고한다. 대상 실패가 새로 생긴 경우까지 잡도록 과제별 대상 실패 발생률을 각 조건에서 구하고 **OFF 발생률 − ON 발생률**도 계산한다. 예외 적용 여부를 확인할 산출물 자체가 없으면 그 지표는 미확정이고 완주 실패는 그대로 센다. 결론의 범위는 일반 Codex 실패가 재현된 합성 상황이다.
- **표본.** 파일럿은 기능별 후보 6~10개, 조건별 3회가 출발 제안이다. 본시험에서는 미사용 후보에 동결된 선별 규칙을 적용하고, 채택 후 OFF/ON 실행 순서만 쌍 안에서 무작위로 바꾼다. 채택된 과제의 재실행과 압축 미발동도 빠짐없이 기록한다.

### 본시험 판정표

본시험 후보를 열기 전에 독립 표본의 단위·최소 수·합격선을 동결한다. 독립 단위는 서로 다른 업무 시나리오인 **과제군**이다. 같은 시나리오의 이름·값 변형과 반복 실행은 한 과제군으로 집계한다. 각 과제군의 비중을 같게 두고 OFF/ON 쌍과 반복을 함께 묶어 재표집한다. 최소 채택 과제군 수는 파일럿에서 정한다. 제안 방법은 기능별 쌍의 변동과 보류율을 반영해 사전에 정한 개선 효과에서 아래 실패 개선 판정식의 검정력이 80% 이상인 최소 규모를 모의실험으로 산출하는 것이다. 동결 기록에는 가정한 효과·오류율, 독립 과제군 최소 수, 후보 모집 상한, 재표집 방법·횟수·난수 시드를 넣는다. 최소 수를 정할 근거가 없거나 이에 미달하거나, 소수 과제군의 결과가 모두 같아서 구간 폭이 0으로 퇴화하면 **탐색적 결과만 보고**한다. 같은 과제의 반복으로 독립 과제군 수를 채우지 않는다.

아래는 파일럿 후 동결할 판정식 초안이다. **하한은 과제군 단위 양측 95% 신뢰구간의 하한**이다. 보류·결측을 양쪽에 유리하거나 불리하게 처리하는 경계값에서 판정이 바뀌면 해당 결론을 보류한다.

| 주장 | 필요한 근거 |
|---|---|
| 특정 실패를 이 기능으로 개선했다 | 독립 비교에서 대상 실패→성공 쌍이 관측되고, 전체 채택 집합에서 **대상 실패 발생률 감소(OFF−ON)**와 **전체 성공률 증가(ON−OFF)**의 하한이 각각 0%p를 초과한다. |
| JIT로 불필요한 열람량을 줄였다 | 감소율 하한 ≥25%, 최종 성공률 차이 하한 ≥−5%p. 낡은 정보 채택이 줄었다는 주장은 해당 실패 발생률로 검증한다. |
| 인계로 무도움 재개 목표를 달성했다 | 무도움 재개 성공률 차이(ON−OFF)의 하한 ≥+15%p. 전체 과제 완주와 첫 산출물 도달은 따로 채점한다. |
| 압축 경유로 총입력을 줄이면서 품질을 유지했다 | 실제 총입력 감소율 하한 ≥15%, 최종 성공률과 초반 예외 적용률 차이의 하한 각각 ≥−5%p. 호출 범위나 실제 입력량이 결측이면 절감 판정만 보류한다. |

다음 후보 모델로의 확장은 해당 기능의 실패 개선이 확인된 뒤에 진행한다. 추가 이점은 충족한 항목만 명시한다. 다른 모델에서도 일반 CLI 실패 선별부터 다시 시작한다.

## Langfuse Cloud에 남길 근거

과제 입력과 기대 결과를 버전이 있는 Dataset에 등록하고, 모델이 볼 수 있는 과제 폴더 밖에서 채점한다. 조건마다 Experiment run을 만들고 동일한 `case_id`·반복 번호를 연결한다. 실행 하나를 대표하는 trace 아래에 CLI 호출, 파일 도구, 인계 작성·재개, 압축·검색·복원, 최종 검증을 관측 가능한 단위로 남긴다. 인계 전후를 별도 trace로 수집할 때는 같은 `trial_id`로 묶는다. [Langfuse 실험 데이터 모델](https://langfuse.com/docs/evaluation/experiments/data-model)

| 기록 단위 | 최소 필드와 증거 |
|---|---|
| 후보 선별 | `phase=screening`, 후보 ID·버전, 일반 CLI 반복별 결과, 예상·실제 실패 유형과 근거, 채택/제외/보류 사유. 본시험 `phase=evaluation`은 채택 근거의 trace ID를 참조한다. |
| 실행 | `case_id`, `trial_id`, 반복, 조건, 과제·채점표 버전, 스냅샷 해시, CLI·kit·압축기 버전, 요청한 모델/사고 수준과 실제 확인 범위, 시작·종료 시각 및 종료 사유 |
| 원본·인계 | 합성 문서 ID·구간, 실제 반환 텍스트의 관련/불필요 추정 토큰, 사용한 토크나이저 버전, 인계 작성·최신 포인터 조회, 첫 유효 산출물의 시각, 재설명·재작업 횟수 |
| 모델·압축 | 스레드/턴/이벤트 식별자, 계수 원천·범위, 입력·캐시 입력·출력의 시작/종료 누계와 차분, 실제 압축 발동·복원의 시각·블록 ID·근거. 캐시 입력이 입력의 부분집합이면 중복 가산하지 않는다. |
| 채점 | 정답·재개·완주·예외 적용 점수와 판정 근거 ID, 테스트 종료값. 사람의 판단이 필요한 개편안은 조건을 가린 뒤 같은 채점표로 평가한다. [Langfuse Score 모델](https://langfuse.com/docs/evaluation/scores/data-model) |

**사용량 사전 점검.** 새 PC의 일반·압축 경유 CLI에서 각각 동일 스레드의 2턴을 `exec`와 `exec resume`로 이어 실행한다. CLI JSONL, 로컬 세션의 사용량 원천, Cloud에 도착한 값과 Score를 대조해 해당 버전의 카운터 범위를 확정한다. Codex 0.171.0의 JSONL 구현은 마지막 스레드 누계를 내보내며 사용량 알림이 없으면 기본값을 반환한다. 기존 합성 로그의 연속 입력 누계는 748,924 → 978,490 → 1,087,099였고 마지막 구간은 108,609토큰이었다. [Codex 0.171.0 JSONL 구현](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/exec/src/event_processor_with_jsonl_output.rs#L109-L119) · [기존 압축 실험 원장](../validation/2026-11-16-astryx-compatibility.md)

- 누계형이면 스레드별 측정 구간의 **종료 누계 − 시작 직전 누계**를 한 번만 반영한다. 새 스레드의 시작값 0은 실제 새 스레드임을 확인했을 때만 쓴다. 인계 작성처럼 기존 스레드 중간부터 잴 때에는 분기 직전의 값을 보관한다. 검증된 스레드별 차분과 새 세션 사용량을 합하고, 중복 이벤트는 식별자로 한 번만 센다.
- 사용량 알림 없는 0, 시작값 불명, 누계 역행·리셋, 종료 시 누락은 해당 구간 결측으로 표시한다. 검증된 호출별 증거가 있어야 호출당 최대 입력량을 보고한다. 압축기 내부 호출의 포함 범위가 불명확하면 전체 순절감 판정을 보류한다. Cloud에는 검증된 차분을 사용량으로 보내고 원누계는 별도 메타데이터로 둔다. Bili의 `tokensSaved`와 열람 추정량은 별도 지표다. [Langfuse 사용량·비용 계측](https://langfuse.com/docs/observability/features/token-and-cost-tracking)
- **JIT 반환 범위.** 앞·중간·끝에 서로 다른 표식을 넣은 긴 합성 출력을 사용한다. CLI 화면/JSONL의 `aggregated_output`과 로컬에서 확인한 모델용 도구 응답을 대조하고 절단된 범위를 확인한다. 표식은 계측기 점검용이다. 본시험은 추적 가능한 실제 반환 구간에만 관련성 라벨과 고정 토크나이저를 적용한다. 대응 관계를 확인할 수 없으면 열람 토큰 지표만 보류한다.

Cloud에는 합성 사례와 허용한 지표만 보낸다. 호스트 사용자 경로, 모델의 내부 사고 원문, 인증 정보, 전체 셸 환경, 실제 프로젝트 원문은 수집 항목에서 제외한다. 제품 저장소 밖에 실험 실행기·fixture·채점표·결과를 두고, 로컬 이벤트와 Cloud 실행은 익명 ID로 연결한다.

## 새 컴퓨터에서 실행하는 순서

1. 인계의 ZIP 해시를 대조하고 실험 폴더에서 공통 설정과 조건별 파일 목록을 준비한다. 일반 CLI와 경유 런타임이 사용하는 Codex 바이너리, Luna/low, 문맥 창·내장 자동 압축 기준을 포함한 유효 설정을 대조한다. 실패 선별에는 JIT 인덱스·지침, 인계, 압축 경유를 넣지 않는다.
2. 일반 CLI에서 인라인 정답 → 단일 파일 읽기 → 수정·테스트를 점검한다. JIT는 긴 도구 출력의 표식과 실제 반환 범위를 대조한다. 동일 스레드 2턴의 로컬 누계·차분과 Cloud 사용량·점수도 대조한다. 압축 경유 조건은 런타임 준비 뒤 독립적으로 같은 점검을 한다.
3. 후보·채점표를 고정하고 세 기능을 모두 끈 일반 CLI만 먼저 실행한다. 실패 재현 근거를 저장한 후보만 기능별 파일럿 비교로 넘긴다.
4. 채택한 인계 과제는 새 CLI 스레드 두 개와 실제 인계 산출물·최신 포인터를 확인한다. 장문 압축은 같은 스레드에서 여러 턴을 지속한다. `exec resume` 등 해당 CLI에서 확인한 수단을 사용하고, 세션 지속이 필요한 시험에서는 `--ephemeral`을 사용하지 않는다. [세션 인계 스킬](../../../kit/skills/session-handoff/SKILL.md)
5. 압축 실험 사본에서 `compression doctor --client codex`, 준비 dry-run, 런타임 준비, 경유 호출 순으로 확인한다. 실제 모델 트래픽과 압축 블록·복원 파일을 검증한다. 환경이 미준비이면 해당 기능을 보류하고 JIT·인계 파일럿은 독립적으로 진행한다. [CLI 압축 준비와 실행](../../../kit/integrations/billion-context/README.md)
6. 파일럿으로 선별·채점 기준, 한도, 지표·결측 처리·표본 규모를 동결한다. 미사용 본시험 후보에도 3단계를 적용한 뒤 채택 과제만 새 OFF/ON 실행으로 비교한다. 선별 기록, 실패 해결률, 전체 쌍의 순개선과 자원 사용량을 함께 보고한다.
